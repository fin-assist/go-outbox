# Автоматизация Renovate (FIN-211)

Контроллер `.github/workflows/renovate-policy.yml` работает с установленным Mend Renovate GitHub App. Сам Renovate продолжает создавать обновления; `automerge: false` сохраняется: слияние выполняет контроллер через обычный GitHub REST API с ожидаемым head SHA, без административного обхода защиты. Команды владельца для обычных PR и release → main сохраняются.

## Ветки и защита

Ровно одна цель: самая новая `release/X.Y.Z`, для которой ещё нет одновременно смёрженного PR из **этого репозитория** в `main` и подтверждения предка через compare API. Если таких веток нет — `main`. Только что созданная от main release-ветка остаётся активной до merge PR. Контроллер обновляет `policy.json` в отдельной ветке `renovate-policy`; рядом `base.json` — точная копия reviewable `renovate-base.json` из выбранной целевой ветки. Источник читается по закреплённому commit SHA только как JSON, код контроллера всегда из default branch. `renovate.json` подключает оба presets в порядке baseline → generated target/quarantine. Ветка содержит только эти два JSON, без кода или workflows. Смена веток, push, завершение CI и получасовая сверка пересчитывают выбор. Hosted Renovate подхватывает preset на следующем запуске; старые PR в прежнюю цель автоматически не сливаются и не закрываются.

Требуются `strict` required status checks с привязкой к GitHub Actions App (15368) и `enforce_admins: true` для **main и release/**. Имена CI — `.github/renovate-policy.json`, дополнительно обязателен `Renovate policy tests`. Другие существующие ограничения сохраняются, обходов для токена нет. Пустой, отсутствующий, pending, skipped или cancelled обязательный check блокирует действие. Проверки текущей попытки PR CI отделены от одноимённых skipped jobs push CI. Чужие дополнительные обязательные проверки также учитываются.

Перед слиянием повторно читаются PR, все коммиты, текущий CI run/attempt и выбранная ветка. GitHub дополнительно проверяет head SHA и защиту ветки. Это несколько REST-запросов: API не предоставляет общей транзакции выбора релиза и merge; административная смена ветки между последним чтением и merge не атомарна. Контроллер не ставит PR в отложенную native auto-merge очередь.

## Только полностью ботские PR

Автор — проверенный Renovate bot ID 29139614, ветка `renovate/` в том же репозитории. Проверяется полный список коммитов (до 250; больше — ручная работа), author ID, действительная подпись и signer=committer `web-flow` или Renovate. Человеческий коммит блокирует автоматические действия, даже если сохранил bot author при cherry-pick. Имя ветки и метка `dependencies` сами по себе ничего не разрешают.

Все AndroidX/Compose обновления, включая смешанные группы, остаются на ручное слияние. Проверяются и metadata Renovate, и фактическое изменение version catalog. Ограничение fragment и существующая группировка сохраняются. UI-тесты контроллер не запускает.

## Повтор и закрытие

Только завершённый failure обязательного CI: контроллер сохраняет общий claim `{sha, runs: {workflow: {run_id, attempt, retried}}}` одним комментарием, затем запрашивает по одному `rerun-failed-jobs` для каждого упавшего обязательного workflow (`CI` и `Renovate policy tests`). Успешный основной CI не скрывает падение отдельного workflow. Частичный повтор сохраняет предыдущие успешные jobs того же run/SHA; старый failure не заменяет отсутствующий job текущей попытки. Повторная доставка события не повторяет запрос. Падение той же SHA после точного следующего attempt каждого повторённого run разрешает закрытие; успешные workflow должны сохранить run/attempt. Успех повтора разрешает обычную проверку слияния. Смена SHA даёт новую независимую попытку; смена run или неожиданный номер attempt оставляет PR владельцу. Ошибка API после claim не приводит к слепому повтору: владелец проверяет run и при необходимости запускает его вручную.

Перед закрытием сохраняется ограничение **точных предложенных значений** зависимостей в generated preset: Dependency Dashboard approval, version-scoped `recreateWhen: never`, изоляция `groupName: null` и новый `additionalBranchPrefix` с номером закрываемого PR. Новая branch identity ещё не существует, поэтому сохранённая старая ветка не обходит запрос approval. Затем тот же комментарий получает проверенный SHA, провалившиеся checks и ссылки, результат повтора и способ возобновления. Ветка не удаляется. Структурированные metadata добавляет сам Renovate через `prBodyNotes`; старые PR без них остаются на ручную обработку.

Повтор той же версии: в Dependency Dashboard отметить Closed/Ignored или Pending Approval. Dashboard создаёт новую изолированную branch identity. Если повтор снова красный, следующий номер PR меняет prefix, и новая попытка снова требует approval. Новые значения версий не совпадают с этим правилом. Digest-обновления ограничиваются точным `newDigest` через `matchJsonata`, а не tag: новый digest того же tag не скрывается. Неудачные точные значения временно изолируются из прежней группы; остальные и новые исправленные значения сохраняют исходные группировки. Это исключение нужно только для контролируемого повтора, а не меняет политику успешных обновлений.

Глобальный `recreateWhen` остаётся стандартным `auto`. После автоматического закрытия controller добавляет recovery rule с `recreateWhen: always` только для затронутой зависимости, datasource и `newMajor` (для digest без major — прежнего tag). Это возвращает исправленные версии той major-линии, которую Renovate иначе мог бы игнорировать целиком после закрытого PR. Recovery rule не меняет имена branches и не делит исходные группы. Более поздние exact failed-value rules задают `never`, approval и отдельный retry prefix: прежние неудачные значения не зацикливаются.

Ограниченный эффект этой политики: после появления recovery rule **любые вручную закрытые обновления той же зависимости, datasource и major** могут возобновляться. Для явного отклонения этой family нужно удалить её recovery rule или добавить более позднее узкое правило approval/never в generated policy (через reviewable PR к этой config-only ветке). Другие зависимости и другие major сохраняют прежнюю семантику ignored. Точные автоматически провалившиеся значения всегда остаются за Dashboard approval. Fixture на настоящем Renovate 44.176.2 проверяет family recovery, сохранение групп, approval и смену retry generation. Hosted App ещё должен подтвердить загрузку preset на следующем запуске: это отдельная проверка активации, не свидетельство уже работающей автоматизации.

## Подготовка и включение

1. Bootstrap generated ветки до мержа `renovate.json` (исходные правила вынесены в `renovate-base.json`, generated preset подключён после них): `GITHUB_REPOSITORY=fin-assist/<repo> RENOVATE_POLICY_TOKEN=<credential> python3 scripts/renovate_policy.py --bootstrap`. Существующая ветка никогда не перезаписывается. Секрет передавать через окружение без записи значения в историю команд.
2. Слить PR реализации по явной команде владельца. Проверить CI и оба review; затем установить строгие защиты на main/release с сохранением всех существующих правил. В `controllerLogin` записать login владельца токена или отдельного App bot.
3. Создать отдельный `RENOVATE_POLICY_TOKEN` (fine-grained PAT или токен отдельного App) только для выбранных репозиториев: Contents, Pull requests, Issues, Actions, Workflows — write; Administration, Commit statuses — read; Metadata — read. Check-runs читает отдельный `GITHUB_TOKEN` с `checks: read`; этот токен не используется для mutations. Не давать bypass. `GITHUB_TOKEN` запрещён для merge: он не запускает необходимые post-merge workflows.
4. Сохранить токен как organisation Actions secret с Selected repositories или repo secret. `allow_auto_merge` не требуется и остаётся выключенным. Сначала проверить bootstrap/preset и fixture major/group и загрузку preset установленным App, затем установить repo variable `RENOVATE_POLICY_ENABLED=true`. При отсутствующем токене контроллер останавливается. По умолчанию он выключен.

Права Automation не ослабляют обычные PR. Токены Claude и чтения Go modules для этой задачи не переиспользуются. Доступ к org secrets может требовать отдельной организации/авторизации; отсутствие доступа не повод печатать значения секретов.

## Проверки

`python3 -m unittest discover -s scripts -p 'test_renovate*.py'` проверяет выбор ветки, SHA/attempt freshness, identity, одиночный повтор, успешный повтор, закрытие с quarantine, дубликаты и ошибки. Запускать с process timeout; workflow использует 60 секунд. Изменения касаются автоматизации, пользовательские сценарии Android не меняются.

Дополнительный contract fixture использует настоящий Renovate `44.176.2`, а не свою копию его алгоритмов: `scripts/test_renovate_runtime.mjs`. Установить эту точную версию через npm в временный каталог с `--ignore-scripts`, затем запустить с Node 24: `RENOVATE_RUNTIME=<temporary npm prefix> node --experimental-test-module-mocks scripts/test_renovate_runtime.mjs`. Обязательно ограничить процесс 90 секундами. Fixture вызывает production `quarantine_rules`, actual branchify/processBranch и Dashboard renderer/parser; внешние network/mutation endpoints заменены фейками. Hosted App execution и очистка stale веток остаются отдельным этапом активации. Контроллер сам ветки не удаляет; обычный lifecycle Renovate может очищать свои старые ветки.

Официальные источники: [preset и ref](https://docs.renovatebot.com/config-presets/), [шаблоны metadata](https://docs.renovatebot.com/templates/), [закрытые major/group PR](https://docs.renovatebot.com/key-concepts/pull-requests/), [Dashboard](https://docs.renovatebot.com/key-concepts/dashboard/), [config](https://docs.renovatebot.com/configuration-options/), [merge REST API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request).

Опубликованные presets: [config-only ветка](https://github.com/fin-assist/go-outbox/tree/renovate-policy).

Проверка опубликованных refs настоящим resolver: `RENOVATE_RUNTIME=<temporary npm prefix> node scripts/verify_renovate_presets.mjs`; ограничить процесс 180 секундами. Для повышения API-лимита можно передать отдельный read credential в `RENOVATE_TOKEN`; код его не выводит.
